# Architecture and custody

Predecessors: [requirements](requirements.md) and [behavior](behavior.md).

Stakeholders are the outside buyer needing fresh revenue evidence, Group
economic operation selecting an earning experiment, Coesite procurement
custodian, Public seller, Engineering supplier and Science source receiver.
The correctness concern is semantic period/concept reconciliation; the
availability/cost concern is bounded first-party procurement; independent
commercial receiving concerns the outside customer rather than test counts.

The existing independent issuer-research-media-service repository, mounted as
Alpaca's child, owns reusable reconciliation and SEC acquisition composition.
Actual supplier intake found the old working tree still tracked inside an
outdated Computer Web parent; current upstream has independent Alpaca and issuer
repositories. Their canonical working paths now use those actual Git stores.
The complete live Alpaca packet constructor moves byte-for-byte to the issuer
owner; Alpaca's existing evidence-packet face delegates through the child
package. The old child identity import had a native missing-export refusal;
its source body/validator contract is preserved, without claiming an unobserved
old identity. The existing child package becomes registry eligible; its default
and old source subpath stay available. New kernel/cohort faces belong directly
to that supplier. No canonicalization or parallel identity implementation is added.

Dependencies flow from Data identity/JSON through ordinary HTTP acquisition to
this Systems issuer-research composition. Generic HTTP serialization is the
platform fetch/Response contract, JSON parsing is Response/JSON with explicit
validation, and source identity uses the existing semanticIdOf supplier.
No new parser, broker, wallet, credential store or settlement engine is born.

Background runtime: Coesite operation + Group instance data -> existing single
EarningClock durable coordinator -> two sequential bounded SEC acquisitions ->
quarter and annual pure reconciliation -> original packet constructor -> one
compact cohort write to its existing STATE R2 bucket. No full companyfacts
payload reaches paid request computation.

Public runtime: customer periodKind + Public instance configuration -> pure
x402 validator -> existing bucket under ISSUER_EVIDENCE binding -> bounded
prepared-object read -> freshness/cohort validation -> selected prepared
comparison -> native market response/settlement. The market retains payment
and fulfillment policy. Neither supplier nor self-run assay can certify
settlement, outside ownership, budget headroom or customer acceptance.

Alternatives: passing raw SEC through repeats the observed stale concept fault;
an LLM summary adds variable cash/semantic cost and is unnecessary for this
bounded task; a ticker directory adds another source and lookup ambiguity,
so this first operation accepts explicit CIKs. A separately published SEC
package would add a release edge without an independent current consumer.

Quality scenarios: invalid request gives no egress; each background pass has
exactly two sequential acquisitions and no hidden retries; source denial leaves
the old complete cohort unchanged and returns a typed retryable error;
historical repeated facts never outrank a later actual period by fy; conflicting
concepts expose ambiguity. Source-memory and timeout ceilings are operation data.
Single-coordinator admission and an unchanged fixed universe bound aggregate
traffic independently of buyer concurrency. Existing Worker request/CPU and
R2 quota headroom need actual artifact/runtime receiving before a release.

Migration/receiving: preserve the actual working public packet API and IDs;
bind the new supplier through its independent package exports; compile catalogue from Public
parameters through the native compiler, native application build and real
public endpoint. Exact source and supplier selection must be received before
promotion. Rollback is the original accepted source/worker release. No active
state is migrated by this stateless capability.
